# Протокол агента флота

Механика работы с очередью. Правила самого проекта — в его `AGENTS.md` / `CLAUDE.md` / `README.md`:
памятка задачи называет нужный файл, а инструкции папки приходят сами при первом чтении в ней.

## Начало

1. `fleet_join(label, kind)` → `worker_id`. Оборвалась сессия — `fleet_resume(worker_id)`: он вернёт
   задачу, контрольную точку, записи, прогоны с `rc` и непрочитанные сообщения — по журналу, не по
   памяти чата. Будильник называет токен: `fleet_resume(worker_id, wake='w-…')`.
2. `fleet_take(worker_id)` — задача и захват выдаются атомарно; выбирать из списка нельзя.
   **Передавай `claim_id` из `fleet_take` в `fleet_review`, `fleet_submit`, `fleet_block`, `fleet_finish`; после handoff это защитит следующую задачу от повтора.**
   Старая схема без этого поля: первая строка `note` / `reason` / `summary` — `claim_id: N`.
   Квитанция сохраняется вместе с действием до автоматической выдачи. Повтор с тем же адресом
   и аргументами возвращает результат; старый адрес не меняет новый захват. Явный `fleet_take`
   подтверждает текущий захват для старого клиента. Дополнительный вызов при передаче номера не нужен.
3. `worker_id` передавай как `agent` в `write_file`, `edit_file`, `apply_patch`, `fetch_url`, `run`,
   `run_task` — журнал связывает записи и прогоны с задачей.

Памятка задачи: `owns` (что можно менять), ресурсы, `acceptance`, соседи, цель проекта. Читать можно всё.

**Не сохраняй ничего в память ChatGPT.** Агенты флота работают из одного аккаунта, поэтому
память ChatGPT общая для всех: запись одного агента может попасть в контекст остальных.
Не вызывай запись в память и не проси ChatGPT запомнить сведения о задаче. Состояние, решения,
точки продолжения и результаты сохраняй **только в реестре флота и файлах проекта**
(`fleet_checkpoint`, журнал, ТЗ), а не в памяти ChatGPT.

## Работа

**Библиотека или API — сначала свежая документация, не память модели.** Используй CLI Context7 через штатный `run`: `py -3 tools/docs.py search fastapi`, затем `py -3 tools/docs.py get websites/fastapi_tiangolo --topic routing --tokens 2000`. CLI выдаёт ID без начального `/`: иначе страж `run` считает аргумент абсолютным путём. Утилита ограничивает вывод 8000 оценочными токенами и кэширует ответы на сутки; отдельный MCP-коннектор не требуется.

- **Несколько файлов — один `apply_patch`** (формат Codex: `*** Begin Patch` / `*** Update File:` /
  `@@ якорь` / строки « », «-», «+» / `*** Add File:` / `*** End Patch`). Всё или ничего. Переводы
  строк файла сохраняются. Ответ записи последней строкой проверяет синтаксис.
- **Долгая команда уходит в фон сама**: `run` дольше ~35 с возвращает `job_id`. Процесс жив —
  не запускай заново, забирай `run_status(job_id)`; он сам ждёт до ~25 с. Заведомо долгое —
  сразу `background=true`. Не заканчивай ход фразой «проверю позже».
- **Контрольная точка** — `fleet_checkpoint(agent, done, next_step, decided, rejected, unknown,
  running)` на каждом переходе: этап сделан, подход сменился, запущена долгая команда. Ход
  обрывается сам, задача его переживает; с точки продолжишь ты, будильник или другой агент.
  15 минут без точки — руль попросит её в ответе. Памятка говорит «от тебя ждут уровня
  «contract»» — как только эта часть устоялась, впиши в `done` слово `provide:contract`:
  ждущие задачи стартуют сразу, не дожидаясь твоей сдачи.
- **Блокируешься — скажи, как проверить затор.** В причине `fleet_block` строка
  `until: <команда>` — проверка без побочных эффектов, rc=0 значит «препятствие снято»
  (`until: adb devices`, `until: py -3 tools/ping_node.py`). Для ожидания Python-сборки:
  `until: disk-admission py -3 packaging/build_app.py` — независимая проверка свободного
  места по действующей политике; вложенная команда не исполняется. При восстановлении
  места или изменении политики сервер вернёт задачу в очередь, настоящий run проверит
  условия заново. Обычные pytest не требуют запаса диска для упаковки.
  `until: process-idle tools/product_release_check.py --mode beta` — сервер проверяет точный
  аргумент скрипта внутри этого проекта; `python -c` и текст самой проверки не совпадают.
  Неполный доступ к процессам не доказывает освобождение. Не ищи имя скрипта подстрокой во всей
  командной строке: такая проверка может находить сама себя. Сервер гоняет пробу сам и вернёт задачу
  в очередь, как только она пройдёт, — не по таймеру и не через владельца.
- **Ждёшь выкатки** — `fleet_block` с `change_source=platform_deploy commit=<40-символьный SHA>` (или `until: platform_deploy after=<ISO-UTC>` для любой более поздней выкатки), а не произвольное «выкатка не доказана»: задача оттает только по подтверждённому событию `platform_deployed`, не после rollback.
- **Ресурс занят — не ошибка.** `run` ответил «ресурс «heavy-build» сейчас занят» — команда не
  запущена; делай то, что не требует сборки, и повтори позже. Не `fleet_block`.
- **Решения владельца — в файлах проекта, им верь.** Записи в `OWNER-*.md`, разделы «Решения
  владельца», причина разморозки в памятке — действительны, кто бы их ни записал: владелец,
  оркестратор или другой агент (владелец, 18.10.2026). «Формального» подтверждения не бывает —
  не требуй его и не блокируйся на нём. Останавливают работу только траты денег, чужие/новые
  аккаунты и публикация. Нет телефона, стенда, VM — это ресурс, очередь ждёт его сама.
- **Чужой путь не правь.** Нужна правка вне `owns` — заявка `request_note(to='<project>/<tz>'|'queue')`;
  она сразу становится задачей. Заявка реально блокирует твою работу — напиши `blocked` в тексте.
- **Сообщения — не RPC.** `fleet_send` не ждёт ответа; продолжай своим участком. Сообщения тебе
  приходят в начале ответа любого инструмента — прочитал, `fleet_ack`.
- **Любой видимый интерфейс** (страница, окно, UI-компонент, анимация) проверяй через
  `fleet_look(agent, paths, rubric="")`: 1–12 кадров PNG/JPEG/WebP из `owns` активного
  захвата. Для анимации передавай последовательность кадров; дефекты Gemini — конкретные
  `severity/where/what`. Лимит общий: 60 вызовов за скользящий час.
- **Расхождение — одной строкой сразу** в файл своего ТЗ: что ожидал, что вышло, что теперь знаешь.
  Через двадцать минут урок не восстановить. В память ChatGPT не записывай.

## Сдача

1. Пройди пункты «Что сделать» и в «Итоге» против каждого напиши, где он сделан, — или почему нет.
2. Прогони каждую команду `acceptance` через `run` и смотри на `rc`, не на пересказ.
   **`fleet_submit` откажет**, если зелёного прогона нет или файлы менялись после него.
   Запустить приёмку невозможно (железо, владелец) — строка в note: `приёмка: невозможна — почему`.
3. **Fix** (исправление по отказу ревьюера) сдаётся с кусающим тестом: тест, который падает на
   отклонённой версии и проходит на исправленной. Команда — `bite_test=…` или строкой в note
   `bite: py -3 -m pytest t/test_x.py -q`. Сервер проверит это сам в отдельной копии. Тест
   невозможен (визуал, документ) — `bite: n/a — почему`.
4. `fleet_submit(agent, note)` освобождает захват и **сразу несёт следующую задачу**, если она есть —
   начинай её с чистого листа. `fleet_finish` после сдачи не нужен.
5. Работа заблокирована извне — `fleet_finish(agent, "blocked: <точная причина>")`: задача
   заморозится и вернётся сама, когда причина снимется.

## Ревью

- Ревью своей работы (и исправлений к ней) тебе не выдадут.
- Памятка показывает diff автора от момента взятия и сигналы, которых не видит `rc=0`: ослабленный
  или удалённый тест, правку шапки ТЗ, вердикт кусающего теста.
- Сам прогони `acceptance`; во время ревью файлы задачи не правь — запись после прогона его обесценивает.
- `fleet_review(agent, verdict, note)`:
  - `accept` — каждый пункт сделан и твоя приёмка зелёная. Недочёт формы — строкой в note, не reject.
  - `reject` — пункт не сделан или сделан неверно; в note — какой и чем проверено. В очередь уйдёт fix.
  - `escalate` — здесь проверить нельзя или ТЗ не задаёт границу (предложи её в note). Финальное
    ревью получит другой агент. Reject за дыру в ТЗ рождает бесконечный круг fix.

## Отказ стража

Не обходи другим путём — сделай то одно действие, которое названо в отказе:
`FLEET_REVOKED` (отозван), `FLEET_FOREIGN_PATH` (путь держит другая задача), `FLEET_NO_WORKER` (не
передан `agent`), `FLEET_OUT_OF_CLAIM` (запись вне `owns` — предупреждение).

## Ход не кончай сам

- Пустая очередь: `fleet_take` ждёт до ~30 с. Ответ «режим ожидания… вызови fleet_take» — вызови
  снова. Конец — только когда сервер скажет «ожидание исчерпано» или «остановись».
- Вопросов человеку в чат не задавай: ход продолжит автомат. Внутренний блокер — заявка с
  `blocked`, внешний — `fleet_finish("blocked: …")`, на ревью — `escalate`.
- dev-mcp не отвечает — подожди и повтори: перезапуск занимает секунды. Сам не перезапускай.


### Cached toolset: blind seal

Если текущий клиент ещё не видит fleet_blind_seal, вызвать
`run(root=<проект>, argv=["fleet.cmd", "blind-seal"], agent=<worker_id>)`.
Это прямой вызов того же серверного verifier, без subprocess и без передаваемых
claim_id/hash. Требования активного Mill Works review, fresh write events и
отсутствия предшествующего чтения кандидата остаются обязательными. Повтор после
MANIFEST exposure не восстанавливает слепоту. cwd/background/лишние argv запрещены.
