# TZ-52 — маршрутизация работы по полосам

Рабочая реализация: `src/dev_mcp/fleet/routing.py`; тесты: `tests/fleet/test_routing.py`. **В рабочем дереве подключено теневое наблюдение `queue.take_next`, но production и enforce не включены.** Реальная выдача не меняется.

## Полосы (lanes)

`lanes(tasks)` получает актуальные зарегистрированные work/fix/request задачи с полями `project`, `tz`, `owns`, `needs`, `kind`; допускаются объекты и словари (у списков `owns/needs` допустим также JSON). Каждая компонента связности отдельного проекта даёт `Lane(name, project, tzs)`.

Два ТЗ связаны, если:

- пересекаются реально нормализованные `owns` с учётом границы сегмента и `/**` (через действующий `model.paths_overlap`), **или**
- одно **непосредственно** зависит от другого по `needs`, и оба имеют общий **кодовый subsystem**; `src/dev_mcp/fleet/*`, `app/android/*`, `ops/probe/*` — примеры. Общая папка `tests/`, `docs/`, `ToDo/` сама по себе не делает цепочку одним subsystem. Для нестандартного дерева можно передать `subsystem` явно. Транзитивные компоненты объединяются.

Нет дополнительной семантической классификации моделью. Одинаковые входы в любом порядке дают одинаковые полосы; имя — `PROJECT/<наименьший tz>`. Ревью/triage не входят в рабочие полосы, независимость ревью сохраняет сама штатная очередь. Два проекта не соединяются даже при совпадении файла.

## Предлагаемая выдача (pick_for)

Интегратор получает **отфильтрованный штатными правилами очереди** ordered ready-list каждой полосы; он не вправе пропускать `needs`, world resources, политику, защищённые пути и гейты независимости. В `LaneState` указываются `lane`, `ready`, `leader` и `leader_alive`.

`pick_for(worker, states)` сначала выбирает следующую задачу из живой полосы, уже закреплённой за `worker`, затем из свободной полосы. Полоса, чьим живым ведущим является **другой** worker, ему недоступна. Если heartbeat ведущего протух и очередь официально признала его неживым, `leader_alive=False` позволяет перевыдать полосу. Сам модуль не решает, жив ли worker, не захватывает locks, не пишет в SQLite и не создаёт новый lease. Порядок кандидатов внутри каждой полосы сохраняется из действующей очереди.

Потеря соединения не означает автоматически смерть worker: интегратор должен использовать действующую серверную проверку liveness, не гадать по времени ответа вкладки. При конкуренции двух `fleet_take` final eligibility и лидерство проверяются **заново внутри транзакции захвата**, иначе возможна выдача одной полосы двум исполнителям.

## Тень — обязательный первый этап

`shadow_pick(worker, states, actual)` вычисляет предложенный TZ и сравнивает с фактически выбранным штатной очередью. Функция возвращает `RoutingObservation(actual, proposed, would_change)` и **ничего не изменяет**.

`queue.take_next` сохраняет `routing_would_pick` с project, именем полосы, worker, actual, proposed, reason, временем и без содержимого задач/переписок, в той же транзакции, что и `take`. История `accepted` сохраняется в графе, чтобы не терять ведущего после успешной сдачи. Это наблюдение не блокирует чужих workers и не меняет выбор при `shadow`. После **24 часов** реального сравнения и разбора расхождений с подтверждёнными false-blocks — отдельное независимое решение о включении `enforce` с быстрым возвратом к `shadow` при ухудшении.

`fleet.cmd why` при интеграции должен показывать понятную причину занятости: **«полоса P/TZ-12 у W123»**, а также свободную/протухшую полосу. Сейчас это только контракт для очереди и пульта, не заявленная существующая функциональность.

## Входной барьер горячего ядра

`spine_blockers(candidate, registered)` — чистый предикат регистрации ТЗ:
раньше зарегистрированный, ещё не `accepted` писатель того же файла из
`controller.py`, `tools.py`, `integrate.py`, `server.py`, `queue.py`,
`review.py` задерживает перевод следующего ТЗ в `ready`. Пересечение
файлов учитывает `/**`; `created_at` задаёт порядок, при его отсутствии —
натуральный порядок TZ. Ревью и другие проекты исключены. Сам переход состояния
выполняет контроллер/регистратор, **не** функция `pick_for`.
Параллельные реализации ядра начинаются лишь после принятого малого ТЗ-контракта
(интерфейс + падающий контрактный тест). Это отдельное правило admission,
не заменяемое блокировкой задачи только при `fleet_take`.

## TZ-57 — проверка запечатанной сдачи, 24 часа в тени

`queue.submit` подключает read-only `acceptance_guard.check` **только после
серверного `claim_submission` для изолированного Git-worktree**. Основание
`base_sha`, checkout и revision берутся из проверенного `ClaimContext` и
sealed submission (`claim_review_bite._submission`), а `owns`, `acceptance` и
путь к ТЗ — из регистрации в реестре через `RegisteredProject.from_store`.
Абсолютный путь зарегистрированного ТЗ пересчитывается относительно исходного
корня для проверки файла **в claim checkout**, не в живом дереве.

Проверка выполняется вне SQLite write-lock; при успешной сдаче её результат
фиксируется в одной транзакции с `submit` как `acceptance_guard_shadow`,
и каждая находка — `would_block` в формате TZ-49. Семейство правила —
`zone`, идентификатор `acceptance_guard:submission`, fingerprint версии
контракта. События содержат claim/submission id, revision, список находок,
`mode=shadow` и `minimum_observation_hours=24`.

**Результат никогда не блокирует сдачу**; ошибка проверки также остаётся
доказательством в shadow-журнале. Для обычной незапечатанной задачи этап
пропускается. Автоперевода `advance/enforce` нет: минимум через сутки
анализа ложных блоков нужно **отдельное решение и изменение интеграции**.
Production-проверка действующего экземпляра dev-mcp остаётся за выкаткой.

## Проверка

`py -3 -m pytest -q -p no:cacheprovider tests/fleet/test_routing.py`

Покрытие: общий файл, `/**`, граница префикса, `needs`-цепочка в одной подсистеме, независимые ветви и проекты, разные порядки входа, исключение ревью, warm worker, запрет чужой живой полосы, передача после подтверждённого offline, shadow без влияния на actual.

**Граница готовности:** тесты доказывают pure planner и запись контрфакта в очереди на изолированном SQLite. Реальная warm-lane выдача, серверная защита от гонок, вывод `why` и суточный replay требуют отдельной интеграционной приёмки; до неё TZ-52 нельзя объявлять включённой на боевой выдаче.
