# Работа локального оператора с флотом

Оператор обслуживает платформу в своём checkout. Веб-агенты работают в
зарегистрированных продуктовых проектах; выдавать им запись в код сервера,
его политики, лончеры и конфигурацию браузера не требуется.

## Перед изменением проекта

1. Выполните `fleet.cmd active "<Проект>"` из каталога установки dev-mcp.
2. Проверьте зоны активных захватов: локальный редактор пишет в обход серверной
   защиты. Не меняйте файлы, принадлежащие другому активному захвату.
3. Для изменения курса используйте `fleet.cmd tell <Проект>/TZ-N "сообщение"`.
4. Зафиксируйте исходный `git status` и сохраняйте посторонние изменения.

## Цикл задачи

ТЗ с YAML-шапкой лежат в `ToDo/tz/` соответствующего проекта. Регистрация,
захват, сдача и ревью проходят через сервер; точные инструменты и форматы —
в [протоколе](FLEET-PROTOCOL.md).

Сервер повторяет приёмку на текущих файлах. Другой агент проверяет результат
по зафиксированным байтам. Интегратор коммитит принятую работу только при
разрешённом `commit = true` и зелёном гейте проекта. Не создавайте такие коммиты
вручную от имени активного захвата.

## Правки платформы

- Меняйте и проверяйте затронутый код в локальном checkout.
- Сохраняйте производственную политику, данные и локальные настройки отдельно
  от исходников. Начальные примеры не заменяют рабочую конфигурацию.
- Проверяйте настоящий вызов инструмента после перезапуска. Успешный
  `initialize` подтверждает транспорт, но не выполнение нужного инструмента.
- Для stdio перезапуском управляет MCP-клиент. При собственном proxy launcher
  используйте настроенный операторский сценарий и проверяйте его итоговый отчёт.
- Обновление расширения и перезапуск MCP-сервера — разные операции.

Текст агента «всё зелёное» не заменяет фактический вывод проверки. Не записывайте
токены и пароли в ТЗ, журналы ревью, Git или сообщения агентам.
