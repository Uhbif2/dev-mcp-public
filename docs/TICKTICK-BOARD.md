# TickTick-доска «🤖 Флот» — рабочее место владельца с флотом

Проект и история решений — `C:\hub\_todo\25-ticktick-fleet-channel.md`. Здесь — как устроено и
что можно менять. Код: `src/dev_mcp/owner/ticktick_oauth.py`, `src/dev_mcp/owner/ticktick_board.py`,
тесты `tests/owner/test_ticktick_board.py` (фейковый TickTick в памяти).

## Подключение

Сервер dev-mcp — сам OAuth-клиент **официального** MCP `https://mcp.ticktick.com` (динамическая
регистрация + PKCE, область `tasks:read tasks:write`). Никаких API Token, Open API и своих REST-клиентов
(решение владельца). Ключ — `data/secrets/ticktick-oauth.json` (маска `*secret*`, агентам не виден),
срок ~180 дней, refresh нет. Переподключить: `ticktick-connect.cmd` (владелец, браузер, «Разрешить»).
Остаток срока — заметка «▶ Флот» в разделе «◎ Система».

Работник `ticktick_board.run_worker` стартует в контроллере (`fleet/controller.py`, рядом с
owner-notices), спит, пока ключа нет, сверяется раз в 2 минуты. Итог каждого цикла —
`data/fleet/ticktick-board-status.json` (`ok`, `sections`, `decided` или `error`) — **смотреть сюда**,
лог сервера никто не читает. Состояние доски (id, журнал своих записей) — `data/fleet/ticktick-board.json`.

## Правила (не нарушать)

1. **Голос.** Флот пишет о работе, не от имени владельца. Без эмодзи-рожиц: знаки ◆ ◐ ▸ ✓ ⋯ ‖.
2. **Чужое не трогать.** Карточки и подпункты владельца сервер не переименовывает и не правит;
   свои объекты — только по журналу `ledger`. etag TickTick не проверяет, но правка меняет только
   переданные поля — поэтому сервер никогда не отправляет поля владельца; теги — слиянием.
3. **Галочка = «сделано».** Решение — пункт чек-листа вопроса. Галочка на карточке — приёмка
   (или «больше не нужно», если до приёмки).
4. **Текст для владельца читается без контекста.** Никаких путей, id задач, кодов стадий и жаргона.
   Карточке нужен `intent/owner-brief.md`; нет или не покрывает вопрос — сервер заказывает его
   флоту (`request:brief-*`, приёмка `py -3 .intent/check.py owner_brief` — серверная копия в проекте; абсолютный путь к `_lib` агентский run отклоняет). Стадия understood пишет его сама.
5. **Заметка не может быть подзадачей** (ограничение TickTick) — статус карточки только тегом и в «Сейчас».
6. **Комментарий в TickTick всегда от аккаунта владельца** — своё сервер отличает по журналу.
7. Сбойное чтение — не удаление: карточку считаем удалённой после двух промахов подряд.

## Что делает сервер с действиями владельца

- **Новая карточка** (или тег `флот`) → `_todo/intents/<ascii-slug>.md` дословно + строка «откуда»
  → штатный конвейер интенций создаёт проект. Карточка остаётся владельца; из «＋ Новое» один раз
  переезжает в раздел своего проекта.
- **Правка текста** → файл перезаписан → новая ревизия интенции; комментарий «вижу правку».
- **Комментарий** → сообщение держателю текущей задачи проекта + `intent/owner-notes.md`.
- **Подпункт** → `request:own-*` (сначала ТЗ в `ToDo/tz-drafts`), `intent/owner-notes.md`, тег
  `в-работе`; отмечен/удалён раньше — заявка замораживается. Итог подпункта: ТЗ, которые
  зарегистрировались в проекте, пока шла заявка (до 10 мин после её accept), все закрыты →
  тег `на-приёмку` + комментарий, что сделано (новых ТЗ нет — «уже в плане»); галочка после
  этого — `owner.ticktick_item_accepted`, а не отзыв.
- **Стадия handed_over пройдена** → карточка остаётся на доске: тег `на-приёмку`, текст «Готово: …»
  из `handover.md` (карточку владельца сервер не переписывает — итог приходит комментарием,
  один раз на версию итога). Галочка → `owner.ticktick_accepted`, карточка уходит с доски
  (`accepted` в состоянии: проект → хеш принятого итога; новый итог — новая приёмка).
- **Галочка варианта** → `owner.ticktick_decision`; для «Одобрить операционный план…» —
  `intent.ops_approved` с sha256 плана (стадия owner_approved закрывается сама).
- **«Не буду делать» / галочка до приёмки / удаление** (и на карточках, которые завёл флот) →
  готовые задачи проекта замораживаются
  (`owner.ticktick_paused`), снятие отметки или восстановление — размораживаются.
